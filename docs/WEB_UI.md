## 0.5 왼쪽 사이드바 읽는 법 (2026-09-17 정리 · 2026-09-18 접기·요약)

토글이 63개다. 이름만 보고 "이걸 켜면 뭐가 좋아지고 뭘 내주나" 를 알 수 없으면 아무도 못 만진다.
그래서 세 가지를 바꿨다.

> **2026-09-18 이후 기본 배치가 바뀌었다.** 사이드바의 토글 블록은 기본으로 **요약 한 줄**
> ("이번 요청 오버라이드: 토글 n · 튜닝 m" + `🧭 Pipeline 에서 편집`)만 보인다(`sidebar_toggles=compact`).
> 아래 ①②③ 의 묶음·배지·축 필터를 사이드바에서 그대로 보려면 블록 제목 줄의 **전체 보기** 를 누른다(`full`).
> 어느 배치에서도 상태는 하나라 프리셋·요청 오버라이드·`💾 내 설정 저장` 이 똑같이 동작한다.
> 사이드바의 모든 블록은 **제목을 눌러 접을 수 있고**(상단 `▲ 모두 접기`), 접힘 상태는 이 브라우저와 계정(`sidebar_collapsed`)에 남는다.
> 900px 미만에서는 저장된 상태가 없으면 기본 접힘으로 시작한다 — 폰·좁은 창에서 토글이 본문을 밀어내지 않게.

**① 파이프라인 순서대로 묶었다.** 위에서 아래로 읽으면 질의가 처리되는 순서가 된다.

| 묶음 | 무엇 |
|---|---|
| ① 검색 — 어디서 찾나 | 채널(fts·vector·graph·external_rag)과 질의 확장. 끄면 그 신호가 아예 없다 |
| ② 근거와 답변 — 어떻게 답하나 | 검증·답변 생성. **LLM 호출이 몰려 있어 시간·토큰의 대부분**을 쓴다 |
| ③ 질의 속도 · 토큰 | 켜면 빨라지고 토큰을 아끼는 것들 |
| ④ 디버깅 · 기록 | 답이 왜 그렇게 나왔는지 되짚기 위한 기록 (품질은 그대로) |
| ⑤ 빌드 — 무엇을 색인하나 | 여기서 끈 것은 질의에서 켜도 쓸 것이 없다 |
| ⑥ 빌드 속도 · 안정성 | 빌드 시간 · 빌드 전후 자가 점검 |
| ⑦ 연동 · 자동화 | 다른 RAG·MCP, 자동 빌드, 자가진화, 화면 부가 기능 |

**② 토글마다 품질/속도/토큰 배지를 붙였다.** 켰을 때 각 축이 어떻게 되는지다.

```
claim_check_llm      품↑ 속↓ 토↓     ← 켜면 품질이 좋아지고, 느려지고, 토큰을 더 쓴다
context_trim         속↑ 토↑         ← 켜면 빨라지고 토큰을 아낀다
log_stages           ·              ← 세 축에 뚜렷한 영향 없음
```

초록(↑)은 좋아지는 축, 주황(↓)은 내주는 축이다. 마우스를 올리면 설명과 함께 한 줄로도 나온다.
근거는 `config.py` 의 `TOGGLE_EFFECT` 이고, **`speed` 프리셋이 끄는 것이 실제로 속도/토큰을 나쁘게
하는 것들인지** 단위 테스트가 대조한다 (표와 프리셋이 서로 다른 말을 하면 배지를 믿을 수 없다).

**③ 축으로 걸러 볼 수 있다.** `전체 · 품질↑ · 속도↑ · 토큰↓ · 켜진 것` + 이름 검색.
"지금 느린데 뭘 끄지?" 는 `속도↑` 를 눌러 켤 것을 고르고, `켜진 것` 으로 지금 무엇이 켜져 있는지 본다.

> 한 번에 바꾸려면 위쪽 **프리셋**이 빠르다 — `speed` 는 LLM 호출을 5회에서 1회로 줄인다.
> 프리셋이 정한 토글에는 왼쪽에 색 띠와 `← 프리셋이름` 이 붙는다.

새 토글을 추가할 때는 `config.py` 의 **세 곳**을 같이 채운다 — `TOGGLE_GROUPS`(어느 묶음), `TOGGLE_HELP`(설명),
`TOGGLE_EFFECT`(세 축). 하나라도 빠지면 `tests/test_review_0917.py::SidebarToggleMetaTest` 가 실패한다.

## 0.6 🧭 Pipeline 페이지 (2026-09-18 · 09-19 구조·흐름 흡수)

질의·빌드·진화·워처 흐름을 **흐름 → 페이즈(국면) → 단계 → trace 노드** 네 단으로 놓고, 국면이나 단계를 고르면 그 자리에서
토글·`config.json` 값·튜닝 파라미터를 보고 고친다. 같은 화면 아래에서 값 하나를 바꿔 가며 **그 키의 단계부터만** 다시 실행해(스윕)
단계 × 값 격자로 비교한다. 보기는 세 가지다 — **블록**(한 흐름 세로) · **지도**(한 흐름 가로) · **전체 흐름**(네 흐름 한 화면).

> **2026-09-19**: 예전 Observability › **구조·흐름** 탭이 여기로 흡수됐다. 같은 레지스트리를 읽기 전용 지도와 편집 화면이
> 따로 그려 "보는 곳과 고치는 곳" 이 갈렸기 때문이다. 예전 주소(`#observability/arch`)로 들어와도 이 페이지로 온다.

사이드바에서 바꾼 토글과 **같은 상태**라 어느 쪽에서 바꿔도 Ask 질의에 함께 실린다. 자세한 사용법은 [PIPELINE_PAGE.md](PIPELINE_PAGE.md).

## 0.65 단계마다 '실측 옆의 시간 제한' (2026-09-19)

trace 폭포의 오른쪽 실측 ms 밑에 `(≤ 10m)` 처럼 **그 단계를 끊을 수 있는 제한**이 붙는다. 단계 표에는 `제한` 열이,
🧭 Pipeline 의 단계 블록에는 점선 칩이, 단계 상세에는 제한 값과 **어느 파일의 어느 키인지**까지 담은 표가 있다.
실측이 제한의 80% 를 넘으면 주황, 넘겼으면 빨강이라 "이 단계가 제한에 걸려 잘린 것인지" 를 한눈에 본다.
값은 `GET /api/limits` 한 곳에서 오고(`llmwiki/architecture.py` 의 `stage_limits()`), 터미널에서는 `python -m llmwiki arch limits` 가 같은 표를 낸다.
자세한 내용은 [PIPELINE_PAGE.md §4.6](PIPELINE_PAGE.md) 과 [CONCURRENCY.md](CONCURRENCY.md).

## 0.66 질의·로그의 '사용자' 열 (2026-09-19)

Observability › **질의·로그**에 누가 낸 질의인지 나온다. 30명이 함께 쓰는 서버에서 "이 질문 누가 했지",
"저 사람 질의만 왜 자꾸 근거 부족이지" 를 이 표에서 끝내기 위한 것이다.

| 요소 | 동작 |
|---|---|
| **사용자** 열 | 사용자 id. 마우스를 올리면 역할 · 창구(web/api/cli/mcp/schedule) · 로그인 방법 · IP · 에이전트 · 연결된 요청 번호 |
| 사용자 이름 클릭 | 그 사용자의 질의만 |
| `사용자 id` 칸 · `내 질의만` · `모든 창구` · `질문에 포함된 말` | 서버에서 걸러 온다 (`GET /api/queries?user=&origin=&q=&limit=`) |
| `#123` 버튼 | 요청 프로파일 탭에서 그 실행의 전체 trace |
| `사용자별 집계` 버튼 | 사용자별 질의 수 · 👍/👎 · 마지막 시각 (`GET /api/query_users`, **admin 전용**) |

가려지는 값은 두 가지다. IP·에이전트는 admin 에게만 보이고, 사용자 id 는 `server.json` 의
`monitor.show_user_to_viewer` 가 `false` 면 본인 것 외에는 `(비공개)` 가 된다 — 진행 중 작업 목록과 같은 규칙이라 한 화면에서 정책이 엇갈리지 않는다.
CLI 는 `python -m llmwiki requests queries` · `requests users` 가 같은 데이터를 낸다 ([CLI_FLOWS.md](CLI_FLOWS.md)).

예전에 쌓인 행에는 사용자 정보가 없어 `—` 로 나온다. `query_log` 테이블에 컬럼만 추가하는 마이그레이션이라 기존 데이터는 그대로 남는다.

## 0.67 Ask 가 세 탭으로 갈렸다 — 질의 · 채널 검색 · 디버그 (2026-09-19)

예전에는 "채널 디버그" 한 탭에 **채널을 하나 고르는 검색**과 **규칙·시간 파싱 테스트**가 섞여 있었다.
성격이 다른 두 가지라 둘 다 좁았다. 이제 셋으로 나뉜다.

| 탭 | 무엇 | 같은 기능의 CLI · MCP |
|---|---|---|
| **질의 · 답변** | 실제 RAG 답변 | `query` · `wiki_query` |
| **채널 검색** | FTS · Vector · Graph 를 **조합해** 돌리고, 행마다 어느 채널이 몇 위로 찾았는지 본다 | `search fts,vector --mode and` · `wiki_search` |
| **디버그** | 검색을 돌리지 않고 **질의가 검색어로 어떻게 변했는지** 본다 (LLM 호출 0) | `inspect "질의"` · `wiki_inspect` |

### 채널 검색 — 복합 조건

채널마다 네 가지 중 하나를 고른다. 섞으면 `(FTS 또는 Vector) 그리고 Graph` 같은 조건이 된다.

| 조건 | 뜻 | API |
|---|---|---|
| **필수** | 이 채널이 반드시 찾아야 한다 (AND) | `require: ["graph"]` |
| **포함** | 이 채널이 찾으면 후보에 들어온다 (OR) | `channels: ["fts","vector"]` |
| **제외** | 이 채널이 찾은 것은 결과에서 뺀다 (NOT) | `exclude: ["vector"]` |
| **끔** | 이 채널은 돌리지 않는다 | 목록에서 빼면 된다 |

`넓게 찾기`(OR) · `모두 일치`(AND) · `실제 순위`(RRF) 는 세 채널을 한 번에 같은 조건으로 맞추는 **빠른 설정**이다.
`실제 순위` 만 성격이 다르다 — 질의 경로가 실제로 쓰는 **가중 RRF** 로 순위를 매기므로, "답변이 왜 이 근거를 골랐나" 를 볼 때 쓴다.
(2026-09-20 에 라벨을 `전부 OR`/`전부 AND`/`RRF 융합` 에서 사람 말로 바꿨다 — 이 화면은 개발자 디버그가 아니라 **사용자용 검색**이다.)

### 채널 검색 — 거르기와 이어가기 (2026-09-20)

| 무엇 | 어디 | 비고 |
|---|---|---|
| **문서 유형 필터** | 검색어 아래 유형 칩 (`issue` `cl` `tc` …, 문서 수 함께) | 여러 개 고를 수 있다. **거르는** 조건이다 — 질의의 `doc_types` 가 *가중치를 올리는* 것과 다르다. API `doc_types: ["issue","cl"]` · CLI `--doc-types issue,cl` · MCP `doc_types` |
| **최근 검색어** | 유형 칩 옆 (최대 8개) | 이 브라우저에만 저장된다(`localStorage`). 누르면 다시 검색 |
| **찾은 말 강조** | 발췌 칸의 `<mark>` | 내가 친 말과 규칙이 넓혀 준 말 — "왜 이게 걸렸나" 가 눈에 바로 보인다 |
| **이 말로 답변 받기 →** | 검색창 옆 | 검색어를 질의·답변 탭으로 옮긴다. 찾기만 하고 끝나지 않게 |
| **📌 고정 근거로** | 결과 행 오른쪽 | "이게 정답인데 왜 안 올라오지" 를 본 자리에서 바로 고친다 (`pins.json`, 조건은 검색어의 앞 단어들) |
| **거른 건수 표시** | 요약 줄 | `유형 필터로 N건 제외` · `권한으로 N건 가려짐` — 사라진 이유를 숨기지 않는다 |
| **결과 없음 안내** | 표 자리 | 유형 필터 풀기 · 제외 해제 · OR 로 바꾸기 · 다른 채널 켜기 · 규칙 설명 보기 |

결과 행을 누르면 그 **문서 화면**(Knowledge › 문서)으로 넘어가고, `chunk` 열을 누르면 그 청크 원문이 표 아래에 펼쳐진다.
여러 채널이 함께 찾은 행은 배경색이 다르다 — 채널 합의가 강한 근거다.
단계별 실행 기록(trace)은 **접힌 채로** 둔다 (필요할 때만 펼친다).

### 디버그 — 질의 해부

다섯 구간을 한 화면에 놓는다: ① 토큰화(검색 토큰·키워드·빠진 불용어) ② 규칙 확장(FTS 식, 규칙 적용 식, 대체 질의, 관련어, 제외, 발화한 규칙)
③ 시간 표현(해석된 범위와 남은 질의) ④ 채널 라우팅(유형과 가중치 막대) ⑤ 고정 근거(pin).

#### 실제 질의와 **같은 것**을 보여 주는가 (2026-09-20 에 고침)

이 화면의 값어치는 "실제로 질의할 때 일어나는 일" 과 같다는 데 있다. 확인해 보니 **세 군데가 달랐다.**

| 단계 | 실제 질의 경로(`query_engine`) | 해부 화면 — 고치기 전 |
|---|---|---|
| 규칙 확장 | `expand(q_search, …)` — **시간 표현을 뗀 뒤**의 말 | `expand(q, …)` — 원문 |
| 채널 라우팅 | `route(q_search, store)` | `route(q, store)` — 원문 |
| 고정 근거 | `match_pins(store, q, route_info["doc_types"])` | `match_pins(store, q)` — 문서 유형 없음 |

그래서 `지난주 ISSUE-2001 의 원인` 같은 질의에서 화면과 실제가 달랐다. 이제 **실제 경로와 같은 순서**로
계산하고, 시간 표현을 뗐으면 `※ 시간 표현을 떼어 낸 뒤 '…' 로 아래를 계산합니다` 를 화면에 적는다.
2번 칸에는 실제로 무엇이 입력됐는지(`입력`)도 보여 준다. 어긋남 방지는 `tests/test_debug_parity.py`(14건)가 맡는다 —
엔진의 호출부 소스를 읽어 같은 인자를 쓰는지까지 본다.

#### ④ 채널 라우팅의 "유형" 이 무엇인가

유형이 하는 일은 **채널 가중치를 정하는 것 하나뿐**이다. 채널을 끄거나 켜지 않는다.

| 유형 | 언제 | 무엇을 한다 |
|---|---|---|
| `keyword` 키워드형 | 짧고 관계를 묻지 않음 (`CL-55302`) | 정확한 용어·번호가 중요 → FTS 에 무게, 의미 검색은 줄임 |
| `semantic` 의미형 | 길고 관계를 묻지 않음 | 표현이 달라도 뜻이 가까운 문단을 찾도록 벡터에 무게 |
| `relational` 관계형 | `왜·원인·누가·영향·관련` 같은 말이 있거나 아는 엔티티가 둘 이상 | 문서 하나에 답이 없어 여러 문서를 이어야 함 → **그래프에 무게를 크게** |
| `hybrid` 혼합형 | 특별한 신호 없음 | 세 채널을 고르게 |

화면은 유형 이름만 띄우지 않고 **왜 그렇게 정해졌는지**를 함께 적는다 —
`관계를 묻는 말이 있음: 원인` · `아는 엔티티가 6개 잡힘` · `숫자가 있어 FTS 가중 +0.3` 처럼 판정에 쓰인 신호 그대로다.
CLI `inspect` · MCP `wiki_inspect` 도 같은 설명을 쓴다(`retrieval.ROUTER_KINDS` 한 곳).

#### 맨 아래 토글 줄 — 무엇이고, 임시로 시험할 수 있나

`query_rules=on · time_scope=on · router=on · …` 줄은 **지금 서버 설정에서 켜져 있는 단계**다.
꺼진 단계는 위 결과에 반영되지 않는다 — `query_rules=OFF` 면 2번 칸이 비어 보이는 것이 정상이다.

2026-09-20 부터 이 칩을 **눌러서 임시로 껐다 켤 수 있다.** 누르면 그 값을 뒤집어 해부를 다시 돌린다.
**요청 단위 오버라이드**라 `config.json` 은 바뀌지 않고, 이 화면을 벗어나면 사라진다(되돌리기 링크도 있다).
영구 변경은 설정 › 파이프라인에서 한다.

#### 낱개 도구 — 위 해부의 한 칸만 따로

위 해부는 질의 하나를 **다섯 단계 전부**로 훑는다. 접힌 칸의 도구들은 그중 **한 칸만** 떼어 다른 입력으로
빠르게 시험한다 — 규칙 사전을 고치는 중이거나 어떤 `chunk_id` 의 원문이 궁금할 때 해부를 다시 돌리지 않아도 된다.
아무것도 저장하지 않는다.

| 도구 | 해부의 어느 칸 | 언제 |
|---|---|---|
| 질의 한 줄 → 확장 보기 | ② 규칙 확장 | 사전을 고친 뒤 효과 확인 |
| 용어 하나 → 규칙 설명 | ② 의 세부 | 이 낱말이 어느 유형·방향으로 퍼지나 (`rules explain` 과 같다) |
| 시간 표현 → 파싱 | ③ 시간 표현 | `지난주`·`8월` 이 어떤 범위가 되나 |
| `chunk_id` → 청크 열기 | — | 검색 결과의 문단 원문 ("이게 왜 걸렸나") |
| `doc_id` → 문서 청크 | — | 문서가 몇 조각으로 나뉘었나 (답이 문단 경계에서 잘렸는지) |

## 0.675 근거에서 원본으로 (2026-09-20)

답변의 근거를 보고도 **원문으로 갈 길이 없었다.** 채널 검색 결과는 이미 문서 화면으로 가는데, 정작
질의·답변의 근거 문단과 그래프 관계 표가 안 갔다. 세 자리를 같은 방식으로 이었다.

| 어디 | 누르면 |
|---|---|
| 근거 문단의 **문서 경로** (`corpus/…/NOTE-….md`) | 지식 › 문서 에서 그 문서를 연다 |
| 근거 문단의 **chunk_id** | 그 문서를 열고 **그 문단을 펼쳐 스크롤**한다 (문단만 따로 보여 주면 앞뒤 맥락을 잃는다) |
| 그래프 관계의 **src·dst 이름** (`CL-55303`, `ISSUE-2003`) | 지식 › 그래프 의 엔티티 상세 — 관계와 **나온 문서 목록**이 거기 있다 |
| 채널 검색의 그래프 관계 표 | 〃 (한쪽만 되면 더 헷갈린다) |

문서 id 가 없는 근거(외부 RAG 결과 등)는 **누를 수 없게** 하고 왜인지 툴팁으로 말한다 — 눌러도 아무 일이
없는 것이 가장 나쁘다.

**서버 쪽 변경 하나**: `/api/entity` 가 `name=` 을 받는다. 그래프 관계 표는 이름만 들고 있어서 화면이
id 규칙(`CL-55303` → `e:cl-55303`)을 스스로 만들어 내야 했는데, 그러면 규칙이 두 곳에 생기고 표기가
조금만 달라도 빗나간다. 서버가 `entity_id_for()` 로 만들어 보고 없으면 엔티티 FTS 로 찾는다.

고치면서 발견: **`LW.openEntity` 는 불리기만 하고 정의된 적이 없었다** — 문서 화면의 엔티티 링크가
예전부터 조용히 아무 일도 하지 않고 있었다. 이제 정의해서 그 링크도 함께 살아났다.

## 0.676 Quality 화면 — 무엇을 보여 줄지 좁혔다 (2026-09-20)

Quality 의 두 화면은 기능은 있었지만 **볼 것이 묻혀** 쓸모가 떨어졌다. 둘 다 "무엇을 먼저
보여 줄지" 의 문제였고, 숫자를 만드는 쪽에서 고쳤다(화면에서만 가리면 CLI·MCP 와 다른 말을 하게 된다).

### Trial 비교 — 0점과 '채점 불가' 를 구분한다

**질의 이력으로 돌린 trial 이 `hit@k 0.000` 으로 보였다.** 채점 엔진은 기대 문서가 없으면
"못 맞혔다" 로 세는데, 실제 질의에는 정답이 없다. 그래서 완전히 실패한 설정처럼 읽혔다.

| 바뀐 것 | 어떻게 |
|---|---|
| 채점할 수 없는 지표 | 목록·비교 모두 **`—`** (마우스를 올리면 "0점이 아닙니다") |
| 목록에 **원천** 칸 | `평가셋` / `질의 이력` — 무엇으로 돌린 trial 인지 한눈에 |
| 원천이 다른 것을 고르면 | 확인을 받고, 비교 맨 위에 **경고 배너** |
| 비교 화면 | *"이 비교에서 읽을 수 있는 지표"* 를 명시 (groundedness · insuf. · ms · 토큰) |
| **`질의 고르기…`** | 문항 원천을 *실제 질의 이력* 으로 두면 나온다. 후보를 **시각·👍/👎·근거 못 찾음·ms·질의문**과 함께 목록으로 보고 **체크해서 고른다**. 고른 것이 있으면 그것만 쓴다 |
| **`A/B 비교 (기준 ↔ 변경) 한 번에`** | 같은 문항으로 지금 설정과 변경본을 연달아 돌리고 바로 비교 |

**왜 고르게 했나**: 기간·건수로 뭉뚱그리면 비교가 내 관심사와 상관없는 문항 위에서 돕니다 —
비교하고 싶은 질의는 대개 *"이 세 질문"* 처럼 정해져 있습니다. CLI 는 `trial candidates` 로 번호를 보고
`trial run --pick 773,772` 로 같은 일을 합니다.

**문항 원천의 기본이 `실제 질의 이력`** 입니다(2026-09-20에 바꿨습니다). 대개 알고 싶은 것은
"진짜로 물어본 질문에서 좋아졌나" 이고, 이 저장소에서는 평가셋 자체가 코퍼스에 색인돼 `hit@k` 가
오염돼 있기 때문입니다. 쓸 만한 이력이 없으면 평가셋으로 물러나되 **어느 원천으로 돌았는지 알립니다**.

### 골랐으면 이제 무엇을 누르나

화면 위쪽 **`다음:`** 줄이 지금 상태에 맞춰 할 일 **하나**를 말해 줍니다.

| 지금 상태 | 다음 |
|---|---|
| 아무것도 안 함 | ① `질의 고르기…` 로 비교에 쓸 질의를 고른다(안 고르면 조건으로 자동) |
| 질의를 골랐다 | ② `설정 오버라이드`(예 `top_k_final=10`)나 프리셋에 **바꿔서 시험할 값**을 적는다 |
| 바꿀 설정을 적었다 | ③ **`A/B 비교 (기준 ↔ 변경) 한 번에`** — 같은 질의로 두 번 돌리고 바로 비교 |
| trial 을 2개 이상 체크했다 | ③′ `비교` |

한 번만 돌려 보려면 `Trial 실행` 입니다 — 그다음 설정을 바꿔 한 번 더 돌리고, 목록에서 **두 줄을 체크해
`비교`** 를 누르면 같은 결과를 봅니다. `A/B 비교` 는 그 과정을 한 번에 합니다.

자세한 내용과 CLI 대응은 [EVAL_TRIAL.md §5.1](EVAL_TRIAL.md).

### 포렌식 — 문제 건부터

기록은 질의마다 쌓이므로 **대부분이 정상 건**이다(이 저장소 실측 1,122건 중 1,025건). 최근 60건을
그냥 나열하니 화면이 정상 건으로 덮여 "왜 답이 부실했나" 를 보러 온 사람이 찾는 줄을 못 봤다.

- 위쪽에 **판정 칩** — `문제만`(기본) · `근거 약함` · `근거 못 찾음` · `기대 결과` · `정상` · `전부`.
  칩마다 **전체 건수**가 붙는다(목록 상한과 무관 — 예전에는 최근 N건만 세어 축소돼 보였다).
- **질의문 검색** 칸으로 좁힌다.
- 옆에 **문제 비율** · **소견이 잡힌 단계** · **제안 종류** · **자주 나온 주제**.

## 0.7 복사 버튼 (⧉)

답변·근거 표·단계 meta·분석 리포트·스윕 표에 **⧉ 복사**가 붙어 있다. 사내 서버는 `http://호스트:8765` 로 접속하는 일이 많은데

1. `navigator.clipboard.writeText` (https 또는 localhost)
2. 숨은 textarea + `document.execCommand('copy')` (http 접속에서 실제로 쓰이는 경로)
3. 그래도 막히면 **본문이 선택된 상태의 창**이 뜬다 — `Ctrl+C`

복사가 안 되는 것처럼 보이면 3번 창이 떴는지 먼저 본다. `verify_buttons.py` 가 2번 경로를 headless 로 확인한다.

## 0.8 창 크기 (반응형)

폭 **360 · 768 · 1024 · 1366 · 1920** 에서 확인한다(`tools/verify/verify_responsive.py`, 폭 5종 × 대표 탭 6종).

| 폭 | 배치 |
|---|---|
| ~900px | 사이드바가 본문 **위로** 접히고 본문이 화면 폭을 다 쓴다. 사이드바 블록은 기본 접힘 |
| ~1200px | Pipeline 3열이 좁혀지고, 분할 보기 열 수가 줄어든다 |
| 그 이상 | 기본 배치 |

규칙 세 가지.

1. **페이지에는 가로 스크롤이 생기지 않는다** (`scrollWidth ≤ innerWidth`).
2. 넓은 표는 자기 상자 안에서만 가로로 스크롤한다(표 자체는 잘리지 않는다).
3. **한 화면에 가로 스크롤 칸이 2개를 넘지 않는다.** 표 하나가 넓어 스크롤하는 것은 정상이지만 여러 개면 레이아웃이 잘못된 것이다
   (하네스가 `overflow-x:auto|scroll` 이면서 실제로 스크롤 중인 칸을 세어 상한을 넘으면 실패시킨다 — `--max-scrollers`).

새 화면을 만들 때 flex/grid 자식에 `min-width:0` 을 주고 긴 `select`·입력에 `max-width` 를 두면 이 검사를 통과한다.
칸을 여러 개 두기보다 **덩어리를 위아래로 쌓아 넓은 표에 전체 폭을 주는 편**이 스크롤을 줄인다(§6.05 의 모델 화면이 그 예).
🧭 Pipeline 은 이 규칙에 맞춰 지도·전체 보기에서 블록을 **줄바꿈**시킨다 — 페이즈마다 스크롤바가 생기지 않는다.

## 1. 활동 표시기 (헤더 오른쪽)

어느 화면에 있든 항상 보인다. **작업 하나가 막대 하나**다.

| 막대 | 뜻 |
|---|---|
| 채워진 파란 막대 | 실행 중인 다른 사람의 요청 (채워진 높이 = 진행률) |
| 채워진 **초록** 막대 | **내 요청** |
| 채워진 주황 막대 | 빌드처럼 쓰기를 하는 작업 |
| 옅은 낮은 칸 | 비어 있는 동시 실행 슬롯 (여유) |
| 점선 막대 | 대기 중 (초록 점선이면 내 요청) |
| `8/8 +2` | 실행 8 / 슬롯 8 · 대기 2 |

막대에 마우스를 올리면 어떤 작업인지, 클릭하면 **진행 중 작업** 화면으로 간다.
테두리가 노랗게 변하면 슬롯이 꽉 찼거나 배타 작업(전체 빌드)이 도는 중이다.

> 이 표시기·질의 화면 요약·진행 중 작업·빌드 화면은 **2초마다 도는 하나의 조회를 나눠 쓴다**.
> 예전에는 화면마다 따로 조회해서, 오래 걸리는 질의가 브라우저의 동시 연결(6개)을 다 쓰면
> 갱신이 밀렸다가 한꺼번에 처리됐다. 지금은 조회가 하나뿐이고 응답이 늦으면 다음 차례를 건너뛴다.

## 2. 탭 고정과 화면 분할

**📌 이 탭 고정** 을 누르면 그 탭이 본문 아래 고정 영역으로 내려가, 다른 탭으로 이동해도 계속 보이고 계속 갱신된다.
서버 모니터와 로그를 켜 둔 채 질의하거나, 빌드 진행을 보면서 포렌식을 여는 식으로 쓴다.

고정 바에서 조절한다.

| 조작 | 뜻 |
|---|---|
| **열** 자동 / 1 / 2 / 3 / 4 | 고정 패널을 몇 열로 늘어놓을지. 자동은 창 너비에 맞춰 늘어난다 |
| **높이** 낮게 / 보통 / 높게 / 자유 | 패널 하나의 높이. 낮게 두면 여러 개를 한눈에 본다. 자유는 내용만큼 늘어난다 |
| 칩 클릭 | 그 패널 위치로 스크롤 (잠깐 반짝인다) |
| 칩의 ✕ / **모두 해제** | 고정 해제 |

패널 머리글의 버튼은 왼쪽부터 ◀ ▶ (순서 이동) · ⟳ (이 패널만 새로 고침) · ⇱ (두 칸 넓게) · ▾ (제목만 남기고 접기) · ✕ (해제) 다.
머리글은 고정되고 내용만 스크롤하므로 패널이 많아도 무엇이 무엇인지 보인다.
창이 좁아지면(820px 이하) 자동으로 1열이 된다.

## 3. 진행 중 작업 (Observability)

**보드**(기본)와 **표** 두 가지 보기가 있고, 선택은 브라우저에 저장된다.

- **용량 게이지**: 동시 실행 슬롯이 몇 칸 찼는지, 대기열 길이, 읽기/쓰기 락 상태.
- **보드**: 한 줄에 작업 하나. 왼쪽 색 띠가 종류(질의 파랑 · 빌드 주황 · CLI 보라 · MCP 초록 · 스케줄 노랑),
  내 요청은 배경이 강조된다. 대기 줄에는 순번이 붙고, 오른쪽에 경과 시간·진행 바·중지 버튼이 있다.
- **표**: 토큰·IP 까지 모두 본다(IP 는 admin 만).
- 넘치면 영역 안에서 스크롤한다. 30명이 동시에 써도 한 번에 훑을 수 있다.

**최근 완료** 에서 `3 ms` 처럼 아주 짧은 것은 실행이 안 된 것이 아니라 **답변 캐시·사전계산 적중**이다.
같은 줄의 `캐시` / `사전계산` 배지가 이유를 알려 준다.

> 캐시는 둘이다. `query_cache`(메모리)와 `precompute`(SQLite 영속). 매번 새로 계산해 보려면 **둘 다** 꺼야 한다.

자기 요청은 누구나, 다른 사람 요청은 admin 이 중지할 수 있다. 중지는 협조적이라 현재 단계가 끝나는 대로 멈춘다.

### 3.1 운영 통계 (Observability › 시스템) — 2026-09-20

이 탭은 **색인 규모**(문서·청크·엔티티 수)와 캐시·워처·유지보수 버튼만 보여 줬다. 운영자가 실제로 묻는
것은 다른 쪽이라("빌드가 왜 느린가", "질의가 언제 몰리나", "디스크가 어디서 커지나") 위쪽에 **운영 통계**
패널을 뒀다. 기간을 고르고 **집계** 를 누르면 계산한다.

| 절 | 보이는 것 |
|---|---|
| `index` | 규모 · 문서당 청크 · 문서 유형별 · **임베딩 없는 청크**(벡터 채널이 그만큼 못 본다) |
| `build` | 마지막 빌드 시각·모드·소요 · **느린 단계 순위** · 빌드 경고 |
| `queries` | 총량 · 하루 평균 · **시간대 막대** · 창구(web/cli/mcp)별 |
| `latency` | p50/p95/최대 + **가장 느린 질의**(요청 번호로 바로 이동) |
| `tokens` | 입력/출력 · 질의당 · LLM 호출/질의 + 가장 무거운 질의 |
| `quality` | 근거 부족률 · 👍/👎 와 피드백이 달린 비율 · 포렌식 판정 · 대기 중 제안 |
| `users` · `storage` · `embed` | 사용자별 상위 · 테이블/폴더별 용량과 **정리 힌트** · 캐시 적중률 |

읽을 때 조심할 것: **표본 수를 먼저 본다.** `latency` 옆의 표본이 3이면 p95 는 사실상 최대값이다.
화면이 표본 수를 함께 보여 주는 이유다. 집계는 읽기 전용이고 기간·표본 상한이 있다.

CLI `stats --full` · MCP `wiki_status(full=true)` 가 **같은 함수**를 쓴다 — [OPS_STATS.md](OPS_STATS.md).

#### 추세 — 일간 · 주간 · 월간 차트 (2026-09-20)

패널 맨 위에 **추세**가 있다. 다른 절이 "지금 얼마인가" 를 말한다면 여기는 **"나아지나 나빠지나"** 에 답한다.
`일간 · 주간 · 월간` 버튼으로 묶음을 바꾸면 기간도 그에 맞춰 늘어난다(일 14일 · 주 12주 · 월 1년) —
월간을 7일치로 그리면 막대가 하나뿐이라 뜻이 없기 때문이다.

| 보이는 것 | 무엇 |
|---|---|
| 요약 4칸 | 최근 구간의 질의 수 · p95 · 토큰/질의 · 근거 부족률, 각각 **직전 구간 대비 ▲▼** |
| 차트 3개 | ① 질의 수(막대) + 빌드 횟수(선) ② 지연 p50·p95(선) ③ 질의당 토큰(막대) + 근거 부족률(선) |
| 구간 표 | 최근 12구간의 원값 (질의·p50·p95·토큰/질의·빌드·근거 부족·👍/👎) |

▲▼ 색은 **좋아졌나**로 정한다 — 지연·토큰·근거 부족률은 내려가면 초록, 질의 수는 올라가면 초록.
차트는 막대·점에 마우스를 올리면 구간과 값이 나온다. 외부 차트 라이브러리를 쓰지 않고
inline SVG 로 그린다(사내망에 폴더째 복사해야 하는 제약 — [SYSTEM_ARCHITECTURE.md §1](SYSTEM_ARCHITECTURE.md)).

**축이 둘인 이유**: 질의 수(364)와 빌드 횟수(15)를 한 눈금에 올리면 빌드 선이 바닥에 깔려 아무것도
읽히지 않는다. 그래서 막대는 **왼쪽 눈금**, 선은 **오른쪽 눈금**을 쓰고 범례에 어느 쪽인지 적는다.
지연(p50·p95)만 단위가 같아 한 눈금을 공유한다. 값이 없는 구간은 **선을 잇지 않는다** — 이으면
없는 추세를 그린 것이 된다.

> 첫 판(2026-09-20 오전)은 좌표계를 가로 15배·세로 4배로 늘려 그려서 **점이 타원이 되고 선이 면으로
> 칠해져** 읽을 수 없었다(CSS 의 계열 색이 `fill:none` 을 덮어썼다). 축·눈금선도 없었다.
> 지금은 비율을 유지해 그리고 축을 둔다. 되돌아가면 `verify_buttons.py` 의 `btn-ops` 가 실패한다.

## 4. 계정별 Web UI 프로파일

헤더의 **💾 내 설정 저장 · ↺ 불러오기 · ✕(삭제)** 로 지금 화면 상태를 내 계정에 저장한다.
다른 PC·브라우저에서 로그인해도 같은 화면으로 시작한다.

저장되는 것: 테마 · 기능 토글 · 프리셋 체크 · 요청 단위 모델/설정 오버라이드 · 질의 모드 ·
고정한 탭 목록 · 분할 보기 상태(열 수 · 높이 · 두 칸 넓게 · 접힘) · 마지막으로 보던 그룹/탭.

- **서버 설정(config.json)은 바뀌지 않는다.** 저장되는 값은 그 사람의 화면 상태와 요청 단위 오버라이드뿐이라,
  다른 사용자의 질의 결과에 영향을 주지 않는다.
- 로그인하지 않은 게스트는 서버에 저장하지 않고 브라우저에만 남는다.
- 저장 위치는 `<data_dir>/profiles.json`, 사용자당 32KB · 최대 1000명.
- 로그인 사용자는 **접속할 때 자동으로 불러온다**.

API: 불러오기는 `GET /api/profile`, 저장은 `POST /api/profile {action:"save", profile:{…}}`, 삭제는 `{action:"reset"}`.
그 밖의 action 이나 빈 `profile` 은 400 으로 거절한다(오타 한 번에 저장해 둔 설정이 지워지지 않도록).

## 5. 상세 분석 리포트와 LLM 소견 (Ask)

질의한 뒤 **📊 상세 분석 리포트** 를 누르면 그 질의 한 건의 모든 단계가 한 장으로 정리된다.
사이드바 토글 `analysis_mode` 를 켜고 질의하면 debug 수준과 프롬프트 샘플까지 들어간다.

| 버튼 | 하는 일 |
|---|---|
| 초점 (전체·품질·속도·토큰) | 그 관점의 소견만 |
| **md 열기** | 리포트 전문을 새 탭에서 |
| **다운로드** | 리포트 전문을 `analysis_req_<번호>.md` 파일로 저장 |
| 클립보드 복사 | 전문을 복사해 다른 LLM 에게 그대로 붙여넣기 |
| **🧠 LLM 소견 받기** | 리포트를 LLM 에게 읽히고 "무엇을 어떤 값으로 바꾸면 좋아지는지" 를 표로 받는다 |
| 소견 → 제안 등록 | 그 소견을 Evolve 제안(HITL)으로 등록해 검토 후 적용 |
| **📦 최적화 자료 묶음 다운로드** | 이 리포트 + **지금 서버의 설정 스냅샷** + 손잡이 지도 + 지시문을 한 파일(`optimize_req_<번호>.md`)로 저장 |
| **묶음 복사** | 같은 내용을 클립보드로 — 바깥 LLM 대화창에 그대로 붙여 넣는 용도 |
| **손잡이 지도만 보기** | 전체 구조와 흐름별 단계표, 각 토글·튜닝 키가 어느 단계에 작용하는지 ([OPTIMIZATION_GUIDE.md](OPTIMIZATION_GUIDE.md)) |

리포트는 서버에도 `logs/analysis/req_<번호>.md` 로 남는다.

**📊 리포트와 📦 묶음의 차이**: 리포트는 "이번 질의에서 무슨 일이 있었나" 만 담는다. 묶음은 여기에
**A 설정 스냅샷**(지금 이 서버의 토글·튜닝 값) · **B 질의 실측**(리포트) · **C 지시문** · **D 손잡이 지도**
를 더해, 바깥 LLM 이 코드를 보지 않고도 "어느 값을 어느 방향으로" 를 답할 수 있게 한다.
받은 제안은 바로 적용하지 말고 `trial run` → `trial compare` 로 회귀를 확인한다([BRINGUP_GUIDE.md](BRINGUP_GUIDE.md) §7.0).
같은 것을 CLI 로는 `python -m llmwiki optimize <번호|last> --focus <렌즈> --out bundle.md`,
API 로는 `GET /api/optimize/bundle?request_id=<번호>&focus=<렌즈>`(`&format=json`) · `GET /api/optimize/guide` 로 얻는다.

LLM 소견은 **리포트 전문이 아니라 우리가 계산한 수치·소견만 추린 요약**을 넘겨서 받는다.
전문에는 질의 확장·claim 검증 같은 다른 작업의 프롬프트 예시가 들어 있어서, 작은 모델이 지시 대신
그 예시 형식을 따라가 버리기 때문이다. 모델이 형식을 못 지키면 원문을 함께 보여 준다.
소견은 **제안**이므로 값을 바꾸기 전에 사람이 판단한다.

## 6. 답변이 같은 말을 반복할 때

작은 모델이 긴 컨텍스트에서 한 구절을 수십 번 되풀이하는 고장이 있다. 지금은 자동으로 처리한다.

1. 반복 구간을 찾아 **그 지점부터 잘라내고**, 왜 잘렸는지 답변 끝과 상단 배너에 표시한다.
2. 그런 답변은 **캐시에 저장하지 않는다** (저장되면 그 질문은 계속 고장 답변을 즉시 돌려준다).
3. 애초에 덜 생기도록 반복 억제 값을 보낸다: `config.json` 의 `llm_frequency_penalty`(0.3) · `llm_repeat_penalty`(1.1).

이미 저장된 고장 답변은 이렇게 정리한다.

```
python -m llmwiki precompute check          # 반복 루프가 들어앉은 항목 찾기
python -m llmwiki precompute clear --broken # 그것만 지우기
```

탐지 기준은 `tuning.json` 의 `answer_repeat_guard` · `answer_repeat_min_chars` · `answer_repeat_times`.
표·목록처럼 정상적인 반복은 잡지 않도록 테스트로 고정해 두었다.

| ① 맨 위 버튼 줄 | 저장 & 프로바이더 재로드 · 전체 연결 테스트 · 실제 호출 테스트(`--live`) · 화면 다시 그리기 · `config.json` 다시 읽기 | "테스트" 는 **저장 전 입력값**으로도 동작한다 |
| ② 전역 설정 3칸 | 임베딩 / 전역 LLM 기본값 / OpenAI-compatible·rerank 엔드포인트 | 역할에서 비워 둔 값이 여기서 상속된다 |
| ③ 모델 · 역할 전체 표 | 역할마다 provider · model · effort (+ '재시도·타임아웃 열 보기' 를 켜면 정책 열) · 실제 인스턴스 · 상태 · 행별 테스트 | 마지막 두 행이 `embed` 와 `rerank(API)` — 임베딩·리랭크 설정은 **여기서만** 고친다 |
| ④ 카탈로그 | `models.json` 목록. 여기 있는 모델이 ③의 드롭다운에 나온다 | 걸러 보기 + `＋ 모델 추가`(접힘) |

**카탈로그 걸러 보기** — 항목이 20줄이 넘어 한 화면을 다 차지했다. 이제 검색(id·설명) · 종류(LLM/임베딩/리랭크) · provider ·
`쓰는 것만`(지금 역할·전역 설정이 실제로 쓰는 모델) · `사용 중만`(enabled) 으로 좁혀 본다. 지금 쓰는 모델 줄에는 **쓰는 중** 배지가 붙고 배경이 다르다.
설명이 길면 한 줄로 줄이고 전문은 마우스를 올려 본다.

**전체 카탈로그 테스트** 는 enabled 항목 전부를 `(provider, model)` 짝으로 ping 한다(`--live` 를 켜면 완성 호출 1회까지). 설정에 쓰기 전에 무엇이
실제로 붙는지 한 표로 본다 — CLI 로는 `models test --catalog [--live]`.

> 배치 근거: 예전에는 전역 설정이 **오른쪽 좁은 칸**에 있어서 열이 12개인 역할 표가 1,000px 도 못 받고 늘 가로로 스크롤했다.
> 전역 설정을 위로 올려 표에 전체 폭을 주고, 역할의 '용도' 열은 역할 이름 아래 두 줄로 접었다.
> 또 `openai_embed_base_url`·`openai_embed_model` 입력칸이 엔드포인트 폼과 embed 행에 **같은 id 로 두 번** 있어
> 저장할 때 어느 칸이 쓰이는지 알 수 없었다 — embed 행 하나로 합쳤다.

## 6.1 역할별 LLM 설정 (Settings › 모델)

역할 표에서 **‘재시도·타임아웃 열 보기’** 를 켜면 역할마다 다음을 직접 편집할 수 있다. 저장하면 `config.json` 의
`llm_roles.<role>` 에 들어간다.

| 열 | 뜻 |
|---|---|
| 타임아웃(초) | 한 번의 호출을 기다리는 최대 시간 |
| 재시도 | 실패 시 다시 시도하는 횟수 |
| 대기(초) | 재시도 사이 기본 대기(지수 증가 + 지터) |
| 총예산(초) | 재시도까지 합친 상한. 넘으면 포기하고 대체 경로로 |
| **출력토큰** | 그 단계가 생성할 수 있는 최대 토큰 |

칸을 **비우면 상속**이고, 회색 글씨가 지금 상속 중인 값이다. 출력토큰의 상속값(단계 기본값)은
라우터 200 · 확장/리랭크 400 · 검증 1500 · 요약 800 · 포렌식 1200 · 리뷰/답변 3000 · 추출 4000 이다.

기본 배포값은 단계 성격에 맞춰 잡혀 있다. 없어도 되는 보조 단계는 빨리 포기하고(확장 30초·리랭크 60초·검증 90초, 각 1회 재시도),
사용자가 기다리는 답변은 넉넉히(240초·2회), 빌드·배치는 길게(추출 120초·리뷰 300초) 둔다.
**끝내 실패해도 답은 나온다** — 답변은 추출식으로, 리랭크는 로컬 휴리스틱으로, 검증은 규칙 판정으로 대체하고
무엇을 무엇으로 대체했는지 답변 상단과 `llm_report` 에 적는다.

같은 값을 CLI 로 보려면 `python -m llmwiki models policy`.

## 8. 다른 권한으로 보기 (권한 미리보기)

헤더의 **👁 권한 보기** 에서 viewer · class3 · class2 · class1 · builder 를 고르면 그 권한으로 화면이 바뀐다.
화면만 바뀌는 게 아니라 **서버가 실제로 그 권한으로 처리한다** — viewer 로 보는 중에는 빌드 요청이 403 으로 막힌다.
지금 미리보기 중이라는 사실은 화면 맨 위 노란 띠로 계속 표시되고, `원래 권한으로` 를 누르면 돌아온다.

**권한은 낮추기만 한다.** 실제 viewer 가 이 기능으로 admin 이 될 수는 없다(쿠키를 직접 위조해도 마찬가지).
그래서 이 쿠키에는 서명을 하지 않는다 — 위조해 봐야 자기 권한을 더 줄일 뿐이다.

| 확인한 것 | 결과 |
|---|---|
| admin → viewer 미리보기 | 역할 viewer, 증분 빌드 403, 질의 200, config 저장 403 |
| 해제 | 역할 admin 복구, 증분 빌드 200 |
| 진짜 viewer 가 `preview=admin` 요청 | viewer 그대로, 빌드 401 |
| 쿠키 위조 `llmwiki_preview=admin` | viewer 그대로, 빌드 401 |

미리보기 없이 **실제 로그인 흐름까지** 확인하려면 인증이 켜지도록 띄운다. `security.json` 의 `mode: auto` 는
"127.0.0.1 로 띄우면 인증을 끄고 자동으로 admin" 이라는 뜻이라, 로컬에서는 로그인 화면 자체가 나오지 않는다.

```
python -m llmwiki serve --host 0.0.0.0 --port 8765
```

이러면 로그인 전에는 `guest / viewer` 로 보이고, 헤더에서 로그인하면 admin 으로 돌아온다.
사내 배포 때 쓸 설정이 그대로 이것이다.

## 9. 이 화면이 원래 이렇게 동작하는 게 맞나 (자가 점검)

버튼을 눌러도 아무 일도 없어 보일 때 먼저 확인할 것.

| 증상 | 확인 |
|---|---|
| 눌러도 반응이 없다 | 결과가 **화면 아래**에 그려졌을 수 있다. 질의 로그의 `trace` 는 결과 위치로 자동 스크롤한다 |
| 포렌식 `진단 실행` 이 안 된다 | request id 를 비워도 목록에서 고른 행·마지막 질의를 쓴다. 정말 대상이 없으면 안내가 뜬다 |
| 코드를 고쳤는데 화면이 그대로다 | 브라우저가 옛 JS 를 쓰고 있다. **Ctrl+F5** 로 강제 새로고침 |
| 여러 사람이 쓸 때 화면이 멈췄다 갱신된다 | `server.json` 의 `concurrency.keep_alive_s` 가 0 이 아닌지 확인 ([CONCURRENCY.md](CONCURRENCY.md) §9) |

자동 점검은 이렇게 돌린다. 버튼을 **실제로 눌러** 화면이 바뀌는지까지 본다.

```
python tools/verify/verify_buttons.py    # 모든 버튼(105개)을 하나씩 눌러 본다 — 격리 환경이라 안전
python tools/verify/verify_click.py      # 중요한 흐름만 빠르게 (요청 프로파일·포렌식·trace…)
python tools/verify/verify_browser.py    # 탭마다 렌더 · 콘솔 오류
python tools/verify/verify_ui_wiring.py  # id·API 경로 배선 정적 검사
```

`verify_buttons.py` 는 설정·DB 를 임시 폴더로 복사하고 mock LLM 으로 서버를 띄운 뒤 버튼을 누르므로
**저장·초기화 버튼을 눌러도 실제 데이터가 바뀌지 않는다.** 판정 기준은 (1) 콘솔 오류가 없을 것,
(2) 눌렀을 때 **무언가 일어날 것**(서버 호출·화면 변화·알림 중 하나), (3) 버튼별 기대 조건 충족.
탭만 보려면 `--only evolve,memory`, 빌드·평가까지 누르려면 `--heavy` 를 준다.

### 용어 (화면의 말 → 뜻)

| 화면 | 뜻 |
|---|---|
| **전체 그래프** (첫 줄) | 엔티티 전체 수 · 그릴 수 있는 수(날짜·금액 제외) · 관계 전체 수(구조 / 공동출현) · 무리 수 · 유형별 수. **몇 개를 볼지는 이것을 보고 정한다** |
| **상위 N개** | 연결(관계 행 수)이 많은 엔티티부터 N개만 그린 것. 전체가 아니다 — "= 전체의 N%" 와 50/120/300/전체 버튼 |
| **무리 #k** | 서로 많이 연결된 엔티티 묶음(라벨 전파). 번호는 순번일 뿐 뜻이 없고 0 은 연결이 가장 많은 노드의 무리, 재빌드하면 바뀐다. 이름 = LLM 요약 첫 문장 또는 대표 엔티티 3개. "요약: 규칙 기본문 / LLM 작성" 은 요약문을 누가 썼는지 |
| **관계 출처** | 관계가 어떻게 생겼나 — explicit(front matter related) · rule(규칙 정규식·ID 링크) · human(사람 승인) · llm(LLM 추출) · cooccur(같은 청크에 함께 등장) |
| **연결 / 이웃** | 연결 = 관계 행 수(청크마다 셈, 실제보다 큼) · 이웃 = 서로 다른 이웃 노드 수 |
| **공동출현 관계 숨김** (기본 켬) | co_occurs·mentions 는 방향도 뜻도 없어 숨긴다. 실DB 는 간선의 96% 가 이것이라 켜지 않으면 구조가 묻힌다 |
