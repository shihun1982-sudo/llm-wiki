무엇을 하는 시스템인가

모뎀 HW 제어 임베디드 SW 조직의 문서(Issue · Change List · SW/HW 설계 · 코딩 규칙 · 주간 보고 · TC …)를 색인해 FTS + 벡터 + 그래프로 검색하고, 근거가 있는 내용만 구조화된 답변으로 돌려주며, 근거가 부족하면 단계적으로 확장 검색한 뒤 insufficient data로 답하고 포렌식을 남긴다. 누적된 포렌식·피드백은 사람이 승인하는 자가진화 제안이 된다.

핵심 흐름

코퍼스 · MCP rawmd + front matter
→
BuildFTS · 벡터 · 그래프(provenance)
→
Query규칙/LLM 확장 → 융합 → 근거 판정 → 답변 → claim 검증
→
Evolve포렌식 → 제안 → HITL

설계 원칙

  • CLI = Web = MCP = eval = trial — 모두 같은 Pipeline.build()/query().
  • 모든 단계는 토글로 on/off, 튜닝 파라미터로 조정, 프로파일 trace(request_id) + 로그(run_id) 로 추적.
  • 설정·규칙·프롬프트·스키마는 전부 파일 — 포팅 시 코드 수정 없음.
  • 외부 API 없이도 동작(추출식 답변·규칙 그래프·hash 임베딩). 붙이면 LLM 단계가 켜짐.

setup\install.bat

python -m llmwiki build --full --trace
python -m llmwiki query "ISSUE-2001 의 원인과 수정 CL 은?" --trace

운영 · 문제 해결

매일 운영

  1. OS 스케줄러가 python -m llmwiki build 호출 (setup/schedule_build.ps1 -Register). 파일 락으로 중복 방지, 실패는 exit≠0 + logs/build.log.
  2. build status / Web › Corpus 에서 진행률·alerts·coverage 확인. 중단되면 다음 build 가 자동 재개.
  3. 주 1회 memory decay, evolve status 로 제안 검토, forensic summary 로 반복 갭 확인.
  4. 튜닝 변경은 trial run/compare 로 전후 비교 후 적용.

디버깅 순서

  1. query "…" --trace → 어느 단계에서 hit 이 0인지, 판정(verdict)·groundedness.
  2. forensic last → 단계별 소견·제안.
  3. logs grep --request <id> → 같은 run_id 의 로그(LLM 호출·오류).
  4. rules test "…" / time "…" / search fts "…" 로 확장·시간·채널 개별 확인.
  5. 수정: rules add, pin add, 문서 추가, 튜닝 → trial compare.
