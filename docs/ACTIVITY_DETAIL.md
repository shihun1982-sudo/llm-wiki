# ACTIVITY_DETAIL — 진행 중 작업 목록에서 **한 줄을 누르면** 무엇이 보이나

> 화면: `관측 ▸ 진행 중 작업` · 데이터: `GET /api/activity` · `GET /api/progress?token=<token>` · `GET /api/request?id=<id>`

## 0. 왜 만들었나

이 화면은 지금 서버에서 무엇이 도는지 훑어보는 목록이었고, **줄을 눌러도 아무 일도 일어나지 않았다**.
그런데 목록을 보는 사람의 다음 질문은 거의 둘 중 하나다.

- 실행 중인 것: **"지금 어디쯤 가고 있지?"**
- 끝난 것: **"그래서 뭐라고 답했지?"**

둘 다 서버에는 이미 있었다. 진행 상황은 `progress.py` 가 단계·로그를 들고 있고, 끝난 결과는
`requests` 테이블과 보관 파일([REQUEST_HISTORY.md](REQUEST_HISTORY.md))에 저장돼 있다. 화면만 이어 주면 됐다.

## 1. 무엇이 보이나

줄(보드 카드 또는 표의 행)을 누르면 목록 바로 아래에 상세가 열린다. 같은 줄을 다시 누르면 닫힌다.

### 실행 중 · 대기 중
- 현재 단계와 단계 경로, 진행률·예상 시간, LLM 호출 중이면 모델과 경과, 대기열 순번
- **진행 기록**(`progress.py` 의 로그) — `▶ 단계 시작` / `✔ 단계 완료 12.3ms` 가 쌓인 것
- 1.5초마다 갱신하고, 끝나면 자동으로 멈춘다 (탭이 보이지 않으면 아예 요청하지 않는다)
- 중지 버튼 (자기 요청은 누구나, 남의 요청은 admin)

### 끝난 것 (최근 완료)
- **그때 저장한 답변**이 그 자리에 바로 보인다 (길면 접어 두고 "전체 보기")
- 걸린 시간 · 토큰 · 근거 수 · 근거 판정 · groundedness · 캐시 응답 여부
- 버튼 셋:
  | 버튼 | 무엇을 하나 |
  |---|---|
  | **↩ Ask 화면에서 열기** | 그때 결과를 Ask 화면에 그대로 복원한다. **다시 실행하지 않는다** |
  | **📄 요청 프로파일** | 관측 ▸ 요청 프로파일로 가서 단계별 워터폴·설정·원본 JSON을 본다 |
  | **⟲ 다시 실행** | 저장된 중간 결과로 특정 단계부터 다시 ([RERUN.md](RERUN.md)) |

## 2. 설계에서 정한 것

**목록 안에서 요약, 한 번 더 누르면 깊이.** 최근 완료는 훑어보는 화면이라, 눌렀을 때 다른 탭으로
튕겨 나가면 "잠깐 확인" 이 안 된다. 그래서 답변 요약은 **제자리**에 펼치고, 더 볼 사람만 Ask 복원이나
요청 프로파일로 한 번에 가게 했다.

**복원은 '내 지난 요청' 과 같은 함수를 쓴다.** 저장된 결과에는 근거 전문(`hits`)이 들어 있지 않다
(요약인 `hits_brief` 만 저장한다 — 파일이 비대해지지 않도록). 그래서 그냥 그리면 화면이 깨진다.
Ask 탭의 `openPastRequest()` 가 이 복원을 이미 알고 있으므로 그 함수를 공개해 **그대로 재사용**한다.
같은 일을 두 곳에서 다르게 하면 한쪽만 고쳐지는 일이 생긴다.

**줄과 작업을 잇는 것은 `data-token` 이다.** 처음에는 카드의 본문 텍스트에서 토큰을 찾아 짝지었는데,
최근 완료 카드는 토큰을 **표시하지 않기 때문에** 짝을 찾지 못해 클릭이 죽어 있었다
(`verify_rerun_ui.py` 가 이걸 잡았다). 지금은 카드·행마다 `data-token` 을 달고 그것으로 잇는다.

**끝난 작업은 폴링을 멈춘다.** 상세를 열면 1.5초마다 진행 상황을 받아오는데, 더 볼 게 없으면 멈춰야
한다. 초기 구현은 "상태가 running 이 아니면 멈춘다" 였는데, **진행 기록이 아예 없는 경우**(끝난 지
오래되어 서버가 정리한 작업)에는 상태 자체가 없어서 조건이 false 였고 타이머가 계속 돌았다.
그 결과 1.5초마다 화면을 다시 그려 **'전체 보기' 로 펼친 답변이 곧바로 도로 접혔다**.
지금은 "진행 정보가 없거나 running 이 아니면" 멈추고, 펼침 상태도 따로 기억해 다시 그려도 유지한다.

**패널은 `brief=1` 로 가져온다.** `GET /api/request?id=N&brief=1` 은 단계별 `trace` 와 근거 전문을 빼고
답변 요약만 준다 — 실측 **60KB → 17KB (72% 감소)**. 이 패널에 필요한 것은 "그래서 뭐라고 답했지?" 뿐이고,
단계별 워터폴이 필요한 사람은 어차피 `📄 요청 프로파일` 로 넘어가 전체를 받는다.

**오래 걸릴 때 "멈춘 것" 처럼 보이지 않게 한다.** 브라우저는 한 사이트에 연결을 6개까지만 연다.
90초짜리 질의가 여러 개 떠 있으면 이 조회가 **브라우저 쪽 연결 대기**에 걸려 늦게 출발한다.
서버는 멀쩡한데 화면만 멈춘 것처럼 보이는 상태다. 그래서 8초가 지나면 문구를 바꾼다:

> 저장된 결과를 기다리는 중입니다 (N초). 지금 **오래 걸리는 질의가 실행 중**이면 브라우저가 연결을
> 재사용할 때까지 이 조회가 밀립니다 — 서버가 멈춘 것이 아니며, 앞선 질의가 끝나면 채워집니다.

**늦게 온 응답은 버린다.** 응답을 기다리는 동안 다른 줄을 누르면, 먼저 보낸 요청의 응답이 나중에
도착해 **엉뚱한 줄에 남의 결과**를 넣을 수 있다. 각 로드는 자기가 시작될 때의 패널 객체를 기억하고,
돌아왔을 때 그 객체가 더 이상 열려 있지 않으면 결과를 버린다.

**끝난 작업 → 저장된 결과의 연결고리는 `request_id` 다.** 요청 관리자의 티켓에 핸들러가 결과를 만든 뒤
`tk["request_id"]` 를 적어 두고, 활동 목록 스냅샷이 그 값을 함께 넘긴다. 이 값이 없는 항목
(이 기능이 들어가기 **전에** 끝난 것, 또는 외부 CLI/MCP 작업)은 진행 기록만 보여 준다.

## 3. 한계

- 진행 기록은 **메모리**에 있다. 서버를 재시작하면 사라진다. 영구 기록은 요청 프로파일과 보관 파일이다.
- 최근 완료 목록 자체도 메모리(`server.json` 의 `monitor.history_size`)다. 더 예전 것은
  `관측 ▸ 요청 프로파일` 또는 Ask 탭의 "🕘 내 지난 요청" 에서 찾는다.
- 저장된 결과는 `keep_requests`(DB 행 수)와 `requests_keep_days`(보관 파일 보존일)로 정리된다.
  그 뒤에는 "저장된 결과를 찾지 못했습니다" 가 뜬다.

| `tools/verify/verify_rerun_ui.py` | 브라우저 검사 (재실행 + 이 화면) |
| `tools/verify/verify_act_detail_load.py` | **로딩이 실제로 끝나는지 시간을 재며** 확인 (처음 열기 · 다시 열기 · 빠른 연속 클릭). 기존 검사는 "결국 보이는가" 를 30초까지 기다려서 봐서 *느린 것*과 *멈춘 것*을 구분하지 못했다 |
