## 1. 쿼리 품질

### 1.1 채널별 실측 (평가 질문 25개, mock LLM 으로 검색만 비교)

| 조합 | hit@k | MRR | avg ms |
|---|---|---|---|
| fts | 0.64 | 0.394 | 77 |
| vector | 0.64 | **0.433** | 29 |
| graph | **0.68** | 0.384 | 34 |
| fts+vector | 0.64 | 0.403 | 63 |
| fts+graph | 0.60 | 0.346 | 52 |
| all (지금) | 0.64 | 0.396 | 72 |

**융합이 최선의 단일 채널을 못 이긴다.** 처음에는 융합 알고리즘을 의심했지만(§1.3) 원인은 다른 데 있었다.

### 1.2 진짜 원인 — 코퍼스에 도구 자신이 들어 있다

문서 352개의 구성을 세어 보니:

| 무엇 | 문서 수 |
|---|---|
| 이 도구의 소스·설정 (`llmwiki/` 49 · `setup/` 19 · `prompts/` 12 · `schemas/` 11 · `js/` 8 · `verify/` 7 …) | **약 127** |
| 이 도구의 산문 문서 (`docs/` 22) | 22 |
| 도메인 문서 (issue 10 · CL 10 · sw_design 4 · weekly 4 · hw_design 3 · tc 3 · 코딩규칙 2) | **38** |
| 공개 RFC (현실적인 코퍼스용) | 나머지 |

도메인 문서가 전체의 11% 뿐이고, 나머지가 검색 결과에서 그것들을 밀어낸다. 실측:

| 코퍼스 | 문서 | hit@k | MRR |
|---|---|---|---|
| 지금 그대로 | 352 | 0.64 | 0.396 |
| − 기계 파일 (소스·JS·스키마·프롬프트·설정예시·도구) | 225 | 0.64 | 0.430 |
| − 위 + 이 도구의 산문 문서(`docs/`) | 203 | **0.80** | **0.483** |
| − 위 + 예제 코퍼스까지 (도메인+RFC 만) | 201 | **0.88** | **0.676** |

이것이 **가장 큰 레버**다. 융합·튜닝을 아무리 만져도 이만큼 움직이지 않는다.

#### 무엇을 바꿨나 (제품)

이전에는 제외 폴더가 코드에 박혀 있어(`EXCLUDE_DIRS`) 운영자가 손댈 수 없었다. 두 가지를 넣었다.

**① `corpus_exclude` 설정** — 코퍼스 안에 있어도 색인하지 않을 경로 패턴.

```jsonc
// config.json
"corpus_exclude": [
  "imported/llmwiki/", "imported/js/", "imported/static/", "imported/themes/", "imported/web/",
  "imported/schemas/", "imported/prompts/", "imported/setup/", "imported/tools/", "imported/verify/",
  "imported/eval/", "imported/legacy/", "imported/misc/", "imported/sample_corpus/"
]
```
- 폴더는 `경로/` · `경로/*` · `경로/**` 중 아무 형태나, 파일은 `**/NOTE-*.md` 같은 fnmatch 패턴.
- `doc_id` 는 코퍼스 폴더 이름으로 시작하지만(`corpus/imported/…`), 그 앞부분을 빼고 적어도 맞는다.
- 바꾼 뒤 **다음 빌드에서 그 문서들이 색인에서 빠진다**(증분으로도 제거된다).
- 워처(`scan_changed`)도 같은 목록을 쓴다 — 다르면 매 주기 헛빌드가 돈다.

**② `health` 의 `corpus_self_index` 경고** — 코퍼스에 이 도구 자신으로 보이는 문서가 5% 넘게 있으면 알린다.
실제 색인에서 **80개(23%)** 로 잡힌다.

#### 적용은 운영자가 정한다

이건 **지식을 빼는 결정**이다. `imported/docs/` 를 빼면 "이 도구를 어떻게 포팅하지?" 같은 질문에 답할 수
없게 된다. 그래서 기능과 경고만 넣고 실제 `config.json` 은 바꾸지 않았다. 도메인 질의 품질이 우선이면
위 블록을 넣고 `python -m llmwiki build` 를 한 번 돌리면 된다 (되돌리려면 목록을 비우고 다시 빌드).

### 1.3 융합 설정은 레버가 아니었다 (가설 기각)

"채널당 후보가 12개인데 `rrf_k=60` 이라 RRF 점수가 1/61~1/72 로 거의 평평해져 순위가 무의미하다" 고
의심했다. 실측은 그 가설을 **기각**한다.

| 설정 | hit@k | MRR |
|---|---|---|
| `rrf_k` 60 / 30 / 20 / 10 / 5 | 0.80 | 0.477 (모두 동일) |
| `rrf_k=2` | 0.80 | 0.467 |
| `fusion_method=weighted` · `minmax` | 0.80 | **0.483** |
| `zscore` | 0.80 | 0.481 |

차이가 MRR ±0.006 이다. 이유는 **융합 뒤에 리랭크와 부스트가 상위 순위를 다시 정하기 때문**이다.
융합은 "후보를 모으는" 역할이고 순위는 뒤 단계가 결정한다. 그래서 기본값을 바꾸지 않았다 —
근거 없는 기본값 변경은 나중에 원인을 찾기 어렵게 만든다.

> 이 과정에서 하네스 실수도 하나 배웠다: `rrf_k` 는 **config.json** 소속인데 tuning.json 에 써 놓고
> 2~60 이 전부 같은 결과라 "영향 없음" 으로 읽을 뻔했다. 손잡이마다 사는 파일이 다르다
> (`tuning.json`: `fusion_method`·`channel_w_*` / `config.json`: `rrf_k`·`top_k_*`).

### 1.4 그래서 손잡이를 미리 만들어 뒀다 — `rerank_fused_w`

"융합 손잡이가 안 먹는다" 를 그냥 두면, 나중에 **정말로** 융합을 조절하고 싶을 때(예: pin 을 확실히
위로 올리고 싶을 때) 방법이 없다. 코드를 보니 리랭크 방식마다 최종 정렬이 제각각이었다:

| 리랭크 방식 | 예전 최종 정렬 | fused 반영 |
|---|---|---|
| `api` | `(-rerank, -fused)` | 동점일 때만 |
| `local` | `(-rerank, -fused)` | 동점일 때만 |
| `cross_encoder` | `(-rerank)` | **전혀 안 함** |
| `llm` | LLM 이 준 순서 그대로 | **전혀 안 함** |

즉 채널 융합(`rrf_k`·`fusion_method`·`channel_w_*`)과 부스트(`time_boost_w`·**`pin_boost`**·
`provenance_boost`·`feedback_boost_w`)가 계산한 점수가 리랭크에서 버려진다. `pin_boost` 가 기본 10.0 으로
큰데도 고정한 근거가 리랭크에 밀릴 수 있었던 이유다.

**넣은 것**

1. `retrieval.final_order(cands, w_fused, ranked=None)` — **네 방식이 모두 이 함수 하나를 쓴다.**
   방식마다 정렬이 다르면 "리랭크 방식을 바꿨더니 pin 이 사라졌다" 같은 일을 추적할 수 없다.
2. 튜닝 손잡이 **`rerank_fused_w`** (기본 `0.0` = **예전 동작 그대로**)

| 값 | 뜻 |
|---|---|
| `0.0` (기본) | 리랭크 점수만으로 정렬. fused 는 동점일 때만 — 지금까지와 완전히 같다 |
| `0.3` | 융합·부스트를 참고 정도로 반영 |
| `1.0` | 리랭크와 같은 비중 |
| `1.0` 이상 | pin·시간 부스트를 확실히 위로 올리고 싶을 때 |

리랭크 점수와 fused 는 척도가 달라서(api 0~1 · local 0~2 · llm 은 남은 개수) **후보 집합 안에서 각각
0~1 로 정규화한 뒤** `rerank + w × fused` 로 합친다. `trace` 의 리랭크 단계 meta 에 `fused_w` 가 찍히므로
"지금 몇으로 돌고 있나" 를 워터폴에서 바로 볼 수 있다.

**기본값을 0 으로 둔 이유**: 지금 코퍼스에서는 융합을 섞어도 좋아진다는 근거가 없다(§1.3). 근거 없이
기본값을 바꾸면 나중에 품질이 달라졌을 때 원인을 찾기 어렵다. 손잡이만 만들어 두고, **쓸 근거가
생겼을 때**(pin 이 밀린다 · 시간 가중이 안 먹는다 · 부스트를 조절하고 싶다) 올리면 된다.

```bat
python -m llmwiki tuning set rerank_fused_w=0.5     :: 반영 시작
python -m llmwiki eval                              :: hit@k·MRR 로 확인
python -m llmwiki tuning reset rerank_fused_w       :: 되돌리기
```
바꾸기 전후를 한 화면에서 비교하려면 워터폴의 **⟲ (rerank 부터)** 로 재실행하는 것이 가장 빠르다
([RERUN.md](../../RERUN.md)) — 검색까지는 재생하고 리랭크부터만 다시 돈다.

## 2. 셀프 이볼브

실제 색인에 제안 88건이 쌓여 있었다 (applied 1 · proposed 87). 내용을 보니 **쓸 수 없는 제안**이 있었다.

```
[synonym] {"term": "nvidia", "expansion": "2026"}   ← 'nvidia' 의 동의어가 '2026'
[synonym] {"term": "nvidia", "expansion": "20"}
[synonym] {"term": "추가",   "expansion": "2026"}
이유: 낮은 융합 점수(0.016): 'nvidia' 질의가 헤딩 '2026년 5월 20일 (수) · … 임원회의' 문단에서만 약하게 매칭
```

헤딩에서 낱말을 뽑아 동의어 후보로 올리는데, 그 헤딩이 날짜였다. 사람이 승인하면 이후 모든 `nvidia`
질의가 `2026` 까지 확장되어 **검색이 망가진다**. 자가진화의 가장 나쁜 실패 방식이다 — 스스로 나빠진다.

원인은 **비대칭**이었다. 같은 함수의 엔티티 후보 쪽(케이스 1)에는 `len(k) < 2 or k.isdigit()` 필터가
있었는데, 동의어 쪽(케이스 2)에는 없었다.

고침: 양쪽(질의 키워드·헤딩 키워드) 모두에 `_usable_term()` 을 적용한다 — 숫자, 2자 미만,
`2026년`·`3분기`·`12일` 같은 날짜 조각, 숫자가 60% 이상인 토큰을 후보에서 뺀다.
회귀 방지: `tests/test_review_0917.py::EvolveProposalQualityTest` (날짜 헤딩 문서로 질의해도 숫자 제안이 안 나오는지).

> 이미 쌓인 87건은 그대로 둔다 — 사람이 승인하기 전에는 아무 일도 일어나지 않고(HITL),
> 지우는 것은 운영자 판단이다. Web 의 **Evolve › 제안(HITL)** 에서 걸러 낼 수 있다.

## 3. 리빌드

**증분 빌드가 전체 빌드와 어긋나지 않는가** 를 네 가지 변화(추가·수정·삭제·이름변경)를 한 번씩 거친 뒤
같은 코퍼스로 전체 빌드한 색인과 대조했다 — `docs` · `chunks` · `chunks_fts` · `embeddings` 모두 일치했다.
증분 반복 뒤 `build verify` 에도 고아 행이 없다.
(`tests/test_review_0917.py::IncrementalRebuildConsistencyTest`)

이름 변경은 특히 잘 동작한다: 해시가 같은 삭제·신규를 짝지어 **임베딩을 재사용**하고 색인만 다시 쓴다.

## 4. 남은 권고 (운영자 결정)

| 우선 | 무엇 | 예상 효과 | 어떻게 |
|---|---|---|---|
| 1 | 코퍼스에서 도구 자신 제외 | hit@k 0.64 → 0.80~0.88 | §1.2 의 `corpus_exclude` + `build` |

1·2 는 색인을 다시 만들어야 하므로 사용자가 적은 시간에 하는 것이 좋다.
