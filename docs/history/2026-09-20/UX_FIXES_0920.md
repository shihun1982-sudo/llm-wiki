# 화면 사용성 수정 — Trial 비교 · 포렌식 · 운영 통계 추세 (2026-09-20)

> **그날의 결정 기록**이다. 지금의 동작은 [EVAL_TRIAL.md](../../EVAL_TRIAL.md) ·
> [FORENSIC.md](../../FORENSIC.md) · [OPS_STATS.md](../../OPS_STATS.md) · [WEB_UI.md](../../WEB_UI.md) 를 본다.

## 1. 요청

> *"web ui를 확인해 봤는데, 잘 안된거 같아.*
> *quality - trial 비교 : 실제 data를 비교 할 수 있게 되어 있는거 맞아? 잘 고민해서 의도에 맞게 사용성을 높혀서 개선해줘*
> *quality - 포렌식 : 잘 고민해서 의도에 맞게 사용성을 높히는 방향으로 개선해줘.*
> *observility - 시스템, 규모 : 여기에 build, query, 등 각종 통계를 넣어서 보여주기로 했자나? 주간이나,, 일간.. 월간 이런것도 차트로 있으면 좋을 것 같아."*

## 2. 먼저 한 일 — 추측하지 않고 **실제 데이터를 봤다**

화면 코드를 읽어 보니 세 기능 모두 "있었다". 그래서 무엇이 잘못됐는지 알 수 없었다.
실제 DB 를 읽어 보고서야 원인이 분명해졌다.

```
trials: 8
  #8 hist2      n=5  hit@k=0.0  ground=0.382  src=queries
  #7 hist-test  n=5  hit@k=0.0  ground=0.259  src=queries
forensics: 1122   sufficient 1025 · weak 76 · insufficient 10 · expectation 9 · ? 2
```

- **Trial**: 질의 이력으로 돌린 trial 이 `hit@k = 0.0` 으로 **저장**돼 있었다. "계산 불가" 가 아니라 0점이다.
- **포렌식**: 기록의 **91%가 정상 건**. 최근 60건을 나열하는 목록은 정상 건으로 덮인다.
- **통계**: 추세 데이터 자체가 없었다.

> 얻은 것: "화면이 이상하다" 는 말에는 **화면이 아니라 데이터를 먼저 본다.** 코드만 읽었으면
> 셋 다 "이미 구현돼 있는데요" 로 끝났을 것이다.

## 3. 무엇이 문제였나 — 셋 다 "보여 줄 것을 고르지 않았다"

| | 기능은 | 문제는 |
|---|---|---|
| Trial | 질의 이력 원천 · 단계별 비교 · 계산 불가 안내가 **이미 있었다** | 목록은 `0.000`, 비교 화면은 "계산 불가" — **두 화면이 다른 말**을 했다 |
| 포렌식 | 목록 · 요약 · 진단 · 기대 결과가 **다 있었다** | 볼 이유가 있는 95건이 정상 건 1,025건에 묻혔다 |
| 통계 | 9개 절이 **다 있었다** | 전부 "지금 얼마인가" 뿐, "나아지나" 가 없었다 |

## 4. 택한 방식

### 4.1 **숫자를 만드는 쪽에서 고친다** (화면에서 가리지 않는다)

셋 다 화면 JS 만 고쳐도 "보기에는" 해결된다. 그렇게 하지 않은 이유는 이 저장소에서 이미 값을 치른
규칙이기 때문이다 — 같은 값을 창구마다 따로 계산하면 **조용히 갈라진다**
([SURFACE_ALIGNMENT.md](../../SURFACE_ALIGNMENT.md)). 그래서:

| 고친 자리 | 그래서 |
|---|---|
| `trials.run_trial` / `list_trials` / `get_trial` | CLI `trial list` · Web 목록 · 비교가 **같은 공백**을 본다 |
| `forensic.list_forensics(verdict, q, only_problems)` | CLI `--only` 와 Web `?only=` 가 **같은 목록**을 준다 |
| `opstats._trend(bucket)` | 터미널 스파크라인 · Web 차트 · MCP 가 **같은 구간 값**을 쓴다 |

### 4.2 채점 불가를 **저장할 때와 읽을 때 양쪽에서** 막는다

저장할 때만 고치면 이미 쌓인 기록(0.0)이 그대로 보인다. 읽을 때만 고치면 새 기록에 0 이 계속 쌓인다.
그래서 `_has_ground_truth(questions)` 로 저장 시점에 `None` 을 넣고, `_mask_ungraded(summary)` 로
읽는 시점에 한 번 더 건다. 판정 근거는 둘이다 — 원천이 `queries` 이거나 `_no_ground_truth` 표식이 있거나.

**택하지 않은 대안**

| 대안 | 왜 안 했나 |
|---|---|
| 화면에서만 `0.0` 을 `—` 로 그린다 | CLI·MCP 는 여전히 0 을 본다. 두 화면이 다른 말을 하는 지금 문제가 그대로 남는다 |
| 질의 이력 trial 을 아예 막는다 | 실제 사용 패턴 위의 지연·토큰·근거 부족률이 **가장 쓸모 있는 비교**다. 막을 것이 아니라 읽는 법을 알려 줘야 한다 |
| 옛 기록을 일괄 UPDATE | 기록을 고쳐 쓰는 일은 되돌릴 수 없다. 읽을 때 보정하면 원본이 남는다 |

### 4.3 포렌식은 **기본값**을 바꾼다 (필터를 추가하는 것이 아니라)

필터만 추가하면 여전히 첫 화면은 정상 건으로 덮인다. 사람은 기본값을 거의 바꾸지 않는다.
그래서 `problems` 를 **기본**으로 두고 `all` 을 선택지로 뒀다. 칩의 건수는 목록 상한과 무관하게
**전체를 센다** — 예전 요약은 최근 500건만 세어 `weak 2건` 처럼 축소돼 보였고, 그러면 문제가 적은
줄 알고 넘어가게 된다.

### 4.4 차트는 **의존성 없이**

외부 차트 라이브러리(Chart.js 등)를 쓰지 않았다. 이 시스템의 제약은 "사내망에 폴더째 복사해서
돌아야 한다" 이고, 그 때문에 웹 서버도 `http.server`, 벡터도 numpy 다
([SYSTEM_ARCHITECTURE.md §1](../../SYSTEM_ARCHITECTURE.md)). 막대·꺾은선이면 "나아지나 나빠지나" 에
답하기 충분해서 inline SVG 로 그렸다(`viewBox` 로 그리고 크기는 CSS 가 정한다).

CSS 는 **탭에 스코프하지 않았다** — `.chip` 이 `#preset-detail` 안에만 정의돼 있어 재사용할 수 없었고,
같은 이유로 앙상블 설명이 깨진 적이 있다(2026-09-20 오전). 화면 공용 요소는 스코프 없이 둔다.

### 4.5 묶음마다 기간이 다르다

'월간' 을 기본 7일로 그리면 막대가 하나뿐이라 아무 말도 하지 못한다. 그래서
`BUCKET_DEFAULT_DAYS = {day: 14, week: 84, month: 365}` 로 두고 `--trend-days` 로 덮어쓰게 했다.

## 6. 화면을 다시 보고 고친 것 (같은 날 2차)

만들어 놓고 실제 화면을 보니 둘이 더 나왔다.

### 6.1 차트가 읽을 수 없었다

| 증상 | 원인 |
|---|---|
| 꺾은선이 **주황 덩어리**로 칠해짐 | `.ch-c0{fill:var(--accent)}` 이 `.ch-line{fill:none}` 을 덮어썼다(같은 특정도, 뒤에 선언) |
| 점이 **납작한 타원** | `viewBox="0 0 100 30"` + `preserveAspectRatio="none"` → 가로 15배·세로 4배로 늘어났다 |
| 값을 읽을 수 없음 | 축·눈금선이 아예 없었고, x 라벨이 3개뿐이었다 |
| 한 계열이 바닥에 깔림 | 질의 수(364)와 빌드 횟수(15), 토큰(243k)과 근거 부족률(0~1)을 **한 눈금**에 올렸다 |

고친 것: 고정 좌표계(780×190)에 **비율을 유지**해 그리고, 가로 눈금선 4칸 + **좌·우 두 축**
(막대=왼쪽, 선=오른쪽; 같은 단위인 p50/p95 만 한 눈금 공유)을 둔다. 눈금은 1·2·5×10ⁿ 으로 떨어지게
올림하고 `243579` 대신 `240k` 로 적는다. 값이 없는 구간은 **선을 끊는다** — 이으면 없는 추세를
그린 것이 된다. `preserveAspectRatio="none"` 으로 되돌아가거나 축이 사라지면
`verify_buttons.py` 의 `btn-ops` EXPECT 가 실패한다.

### 6.2 "과거 질의를 어디서 고르나"

사용자 지적: *"여기서 과거 질의를 어디서 선택할 수 있어? 선택을 해야 비교를 하지"*.
맞는 지적이었다 — `--source queries` 는 기간·건수·피드백으로 **뭉뚱그려** 가져갈 뿐, 무엇이 들어가는지
보여 주지도, 고르게 하지도 않았다. 비교하고 싶은 질의는 대개 *"이 세 질문"* 처럼 정해져 있다.

- `evalset.pick_questions(store, ids)` — 고른 `query_log.id` 로 문항을 만든다(원천 `kind="list"`).
- `GET /api/eval/candidates` · CLI `trial candidates` — 같은 후보 목록(번호·시각·👍/👎·근거 못 찾음·ms).
- 실행: Web 은 체크박스 목록, CLI 는 `trial run --pick 773,772,771`.
- 없는 번호는 **조용히 버리지 않고** `missing` 으로 알린다 — 조용히 버리면 문항이 왜 줄었는지 알 수 없다.

### 6.3 이 화면들이 왜 옛 동작을 보이고 있었나

사용자 화면이 고친 뒤에도 옛 동작(원천=평가셋, `hit@k 0.000`)을 보였다. 원인은 **서버 프로세스**다 —
정적 JS·HTML 은 요청마다 디스크에서 읽히지만 **Python 모듈은 기동 시점에 적재**된다. 그래서
새 화면 + 옛 계산이 섞였다. 코드를 고친 뒤에는 `serve` 를 다시 띄워야 한다.

### 6.4 "이거 앙상블로 동작한건가?"

사용자가 `answer_llm` 단계 JSON 을 보고 물었다. 단서는 `"model": "llama3.1+llama3.1+llama3.1"` 의
**`+` 하나뿐**이었고, `counters.llm_calls: 4`(멤버 3 + 취합 1)로 겨우 뒷받침할 수 있었다.
멤버별 내역은 결과(`r["ensemble"]`)에만 있고 trace 로 올라오지 않아 **어느 창구에서도 보이지 않았다.**

`answer.summarize_ensemble()` 을 만들어 단계 meta 에 싣고, Web(배지 + 멤버 표)·CLI(`--trace` 멤버 줄)·
MCP(같은 meta)가 같은 값을 쓰게 했다. 설계에서 정한 두 가지:

- **막대는 가장 느린 멤버 기준.** 멤버는 병렬이라 ms 합이 단계 시간이 아니다 — 순차로 그리면
  "3배 걸렸다" 로 읽힌다.
- **멤버 본문은 싣지 않는다.** trace 는 요청마다 저장되므로 크기가 배로 늘고, 읽을 일도 드물다.

같은 화면에서 사용자의 설정 문제도 드러났다 — 멤버 셋이 **전부 같은 모델**(`llama3.1`)이라
다양성은 없고 비용만 3배였고, `cited: []` 로 **취합기가 인용을 버리고** 있었다(문서에 읽는 법을 적었다).
