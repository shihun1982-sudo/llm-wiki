## 1. 품질

### 1.1 측정된 품질 지표

| 지표 | 값 | 출처 |
|---|---|---|
| hit@k · MRR (코퍼스 위생 개선 전→후) | 0.64 → **0.88** | README.md:126 |
| trial baseline p95 | 10.53 ms (n=25) | CLI_FLOWS.md:536 |
| 실 LLM 인용 | **인용 0개 · citation_precision 0.0** | `verify_live_models_result.json` |
| 실 LLM eval hit@5 | `hit@k=None` (평가셋 미실행) | 〃 |

**가장 큰 품질 신호는 튜닝이 아니라 코퍼스 위생이었다.** 이 도구 자신의 소스가 색인되어 도메인 문서를 밀어내고 있었고,
제외하니 hit@k 가 0.64 → 0.88 로 올랐다 (README.md:126). health 가 지금도 `자기 소스 색인 80개=23%` 를 warn 으로 보고한다 (CODE_REVIEW_0917.md:15).

**실 LLM(Ollama llama3.1) 로 돌렸을 때 인용이 0개** 라는 것은 심각한 신호다. 답변은 나오지만 `[C#]` 를 달지 않는다 —
작은 모델이 인용 지시를 따르지 못하는 것이므로, 모델 문제이지 파이프라인 결함은 아니다. 다만 **`claim_check` 가 이를 걸러내지 못하고 있다**:
groundedness 가 0 인데도 답이 그대로 나간다. 운영 환경에서는 `claim_policy` 를 `drop` 또는 `annotate` 로 두고
`answer` 역할에 인용을 지키는 모델을 배정해야 한다.

### 1.2 이번에 넣은 품질 손잡이: 규칙 효과 측정

동의어·약어 규칙은 LLM 없이 recall 을 올리는 가장 값싼 수단인데, **쌓이기만 하고 줄지 않았다.**
지울 근거가 없으니 잘못 넣은 규칙이 계속 엉뚱한 문단을 끌어온다.

이제 질의마다 규칙별로 넷을 센다 — 걸렸나(`fired`) · 후보를 가져왔나(`cand`) · **최종 컨텍스트에 들어갔나**(`helped`) · 인용됐나(`cited`).
대체 질의 리스트마다 출처 규칙을 달아 두므로 여러 규칙이 동시에 걸려도 공적을 뭉개지 않는다.

읽는 법: `fired` 가 큰데 `helped` 가 0 이면 **노이즈만 만드는 규칙**이다. `rules effect --order useless` 가 그것만 뽑는다.
상세는 [QUERY_RULES.md §4.5](../../QUERY_RULES.md).

### 1.3 품질을 더 올릴 수 있는 자리 (제안)

| 제안 | 근거 | 예상 효과 |
|---|---|---|
| **평가셋을 실 코퍼스로 다시 만든다** | 실 LLM 실행에서 `hit@k=None` — 평가셋이 지금 코퍼스와 맞지 않는다 | 회귀 평가가 실제로 동작하게 된다. 지금은 빈 평가셋이면 양쪽 0 이라 **무엇이든 '악화 아님'** 으로 통과한다 (CODE_REVIEW 지적) |
| **자기 소스 색인 제외를 기본값으로** | health warn `자기 소스 23%` | 0.64 → 0.88 의 재현 |
| 문맥 조건부 규칙(`when`/`unless`) | 같은 약어가 모듈마다 다른 뜻 | 규칙 효과 데이터가 쌓인 뒤 판단 |

### 3.2 30명 운영 시 예상 비용 (파생 — 실측 아님)

하루 1인 20질의 · 30명 = 600질의. 실 LLM 기준 9,910 토큰/질의라면 **하루 약 595만 토큰**.
`speed` 프리셋이나 `claim_check_llm` off 로 **절반 이하**로 떨어진다. 이 수치는 위 실측의 단순 곱이며, 실제 코퍼스·질의 길이에 따라 달라진다.

### 3.3 토큰을 줄이는 자리

`llm_roles.<역할>.max_tokens` 가 단계마다 따로 있다 (router 200 · expand/rerank 400 · verify 1500 · answer 3000 · extract 4000).
**출력 토큰 상한을 줄이는 것보다 입력을 줄이는 쪽이 효과가 크다** — 질의 1건의 in/out 비가 1,526 : 36 이다.
입력을 줄이는 것은 `top_k_final`(컨텍스트 청크 수) · `context_max_chars` · `rerank_candidates` 세 값이다.

### 6.2 이번에 고친 안정성 항목

- **빌드가 48시간까지 살아 있게** 했다. 동시에 `read_wait_timeout_s` 는 900 으로 **일부러 남겼다** —
  이 값을 48시간으로 올리면 전체 재빌드 동안 질의 스레드가 쌓여 서버가 마비된다. 빌드가 아니라 **질의의 수명**이기 때문이다.
- **자동 적용이 사람 없이 전체 리빌드를 돌리지 못하게** 종류를 제한했다.
- **스냅샷 무한 증식**을 막았다 (`data/snapshots/` 가 1.4 GB 까지 자라 있었다).
- 스케줄 편집기가 **모르는 필드를 지우지 않게**, 이름 변경이 **작업을 잃지 않게** 고쳤다.

| 위험 | 증거 | 제안 |
|---|---|---|

### 6.4 문서 수치의 자기모순 (신뢰성 문제)

청크 수가 문서마다 **16,892 / 16,894 / 16,896** 세 값이고, DB 크기도 503 MB / 480 MB / 실측 476.2 MB 로 다르다.
