# LLM Wiki RAG — 구현 브리프 (요구사항 + 가이드; 세부 구현은 구현자 재량)

> 이 문서는 "무엇을, 왜, 어떤 기준으로" 만들지를 정의한다. "어떻게" 는 구현자(LLM/개발자)가 결정한다.
> 현재 구현과 동일하게 재현하려면 [REBUILD_SPEC.md](REBUILD_SPEC.md) 를 대신 사용하라. 이 브리프는 다른 기술 선택(다른 DB, 프레임워크, 언어)도 허용한다.

---

## 1. 배경과 목표

사내 문서(회의록, 일정, 시장 리포트, 논문 PDF, CSV 실적표 등 수천 개, 매일 수십 개 추가)를 대상으로 **정확한 근거를 인용하는 질의응답 위키**를 만든다. 운영자는 검색 파이프라인의 각 단계를 켜고 끄고, 수치를 조정하고, 요청 단위로 무엇이 얼마나 걸렸는지 확인하며, 사용 중 드러나는 데이터 결함을 통제된 절차로 반영할 수 있어야 한다.

성공 기준(요약): (a) 외부 API 없이도 동작, (b) 3,000+ 문서 · 일 20건 추가를 증분으로 감당, (c) 평가셋 hit@5 ≥ 0.95, (d) 모든 단계가 관측 가능·조정 가능, (e) 자가 진화는 사람이 승인하는 안전한 루프.

## 2. 필수 요구사항 (MUST)

### 2.1 색인 (Build)
- R1. 지정한 폴더들을 재귀 스캔해 `.md .txt .csv .html .pdf` 를 문서로 읽는다.
- R2. 헤딩 구조를 보존하는 청킹(섹션 → 문단 경계 분할, 오버랩). 청크는 `문서/헤딩 경로/오프셋` 을 유지한다.
- R3. 세 가지 색인을 만든다: 키워드(BM25/FTS, 한국어 조사 변형 흡수), 벡터(오프라인 기본 임베더 + 외부 임베더 선택), 지식 그래프(엔티티·관계·멘션).
- R4. 그래프는 **규칙 기반(사전+정규식, 비용 0)** 과 **LLM 기반(선택)** 두 경로로 만들고 병합한다. 각 노드는 **어느 문서/청크에서 왔는지(문서 참조)** 를 직접 가진다.
- R5. 증분 빌드: 변경/추가/삭제된 문서만 재처리. 변경 감지는 파일을 읽지 않고(stat) 수 십 ms 안에 끝나야 하며, 변경 없는 빌드는 전 단계를 건너뛴다.
- R6. 자동 반영: 서버 실행 중 주기적으로 변경을 감지해 증분 빌드하는 워처(또는 동등한 수단).
- R7. 엔티티별 위키 페이지(설명·문서 참조·관계·근거)를 생성하고, 사람이 페이지에 적은 편집 노트는 다음 빌드에 재색인된다.

### 2.2 질의 (Query)
- R8. 하이브리드 검색: 키워드 + 벡터 + 그래프 결과를 융합(RRF 등)하고, 리랭크(LLM / 크로스인코더 / 로컬 휴리스틱 중 선택) 후 컨텍스트를 구성한다.
- R9. 질의 유형(키워드형/관계형/서술형)에 따라 채널 가중치를 바꾸는 라우터.
- R10. 답변은 LLM(모든 사실 문장에 `[C#]` 인용 강제, 없는 내용은 "확인되지 않음") 또는 LLM 없을 때 추출식 폴백.
- R11. 토큰·지연 절감 수단을 각각 on/off 할 수 있어야 한다: 질의 캐시, 컨텍스트 압축, 중복 청크 제거, LLM 리랭크 생략 등.

### 2.3 모델 설정
- R12. 임베딩 모델, 리랭크 모델, 답변(chat) 모델을 **각각** 설정할 수 있어야 한다. 역할(answer / rerank / extract / summary / review)별로 provider·model·effort 를 다르게 두고, 비운 항목은 전역값을 상속한다.
- R13. 설정 경로 3가지가 같은 키를 쓴다: 설정 파일, CLI, Web UI. 연결 테스트(토큰 소비 없이)가 있어야 한다.

### 2.4 관측성 (Observability)
- R14. 모든 단계는 프로파일 trace 를 남긴다: 소요 ms·시작 오프셋·요약 메타·SQL 문 수·LLM 호출/토큰·건너뛴 사유·오류. 디버그 레벨(0 요약 / 1 상세 메타 / 2 프롬프트·응답 원문)을 요청 단위로 지정.
- R15. **모든 요청(query/build/eval/search)** 의 trace 와 설정·결과가 저장되어 나중에 요청 단위로 열람·비교할 수 있다.
- R16. 단계별 튜닝 파라미터는 코드 상수가 아니라 **별도 파일**에서 제어하며, 각 파라미터에 설명·impact·예시·범위·재빌드 필요 여부가 붙는다. 문서(표)는 레지스트리에서 자동 생성한다.
- R17. 전체 구조와 흐름(질의 / 빌드 / 자가진화 / 워처)을 도식으로 보여주는 화면이 있고, 단계마다 관련 토글·설정·튜닝·CLI·impact 와 마지막 실행 시간을 겹쳐 보여준다.

### 2.5 자가 진화 (Self-Evolving)
- R18. 질의 캡처(시드 없음·낮은 점수·무인용 답변), 👍/👎 피드백+정정문, LLM 리뷰가 **데이터 수정 제안**(동의어·별칭·엔티티·관계·위키 노트)을 만든다. 코드/프롬프트 변경 제안은 금지.
- R19. 제안은 기본 HITL(사람 승인). 적용 시 스냅샷 → 적용 → 재색인 → 회귀 평가 → 악화 시 자동 롤백, 이력은 체크섬과 함께 기록.

### 2.6 인터페이스
- R20. CLI 와 Web UI 는 기능 집합이 같다(Web 콘솔에서 CLI 를 그대로 실행 가능). 모든 토글은 CLI 플래그·API 오버라이드·UI 체크박스 이름이 동일하다.
- R21. 외부 에이전트 접근용 표준 인터페이스(MCP) 를 읽기 전용으로 제공한다.

### 2.7 비기능
- R22. 표준 라이브러리 위주(HTTP 서버 포함), 단일 파일 DB, Windows/한글 경로 지원. Python 3.7 호환이 요구되면 문법 제약을 지킨다.
- R23. 회귀 테스트: 빌드·증분·질의·토글 skipped·자가진화 적용·프로파일 필드·튜닝 검증·MCP 를 자동 테스트로 커버.

## 3. 구현자 재량 (SHOULD / MAY)

- 저장소: SQLite(FTS5) 권장이나 동등한 기능이면 다른 선택 가능. 벡터 ANN 인덱스는 선택.
- 임베더: 오프라인 기본(hash n-gram 등)은 필수, 의미 임베더(voyage/bge-m3 등)는 선택.
- 리랭크: 크로스인코더는 선택(없으면 로컬 휴리스틱으로 폴백).
- 커뮤니티 탐지·요약, LLM 질의 확장, PRF, 인접 청크 확장 등 품질 옵션은 **토글/튜닝으로 끌 수 있는 한** 자유.
- UI 기술: 빌드 도구 없는 바닐라 JS 를 권장하지만 강제하지 않는다.

## 4. 아키텍처 가이드 (권장 형태)

```
config(설정·토글) + tuning(단계별 파라미터 레지스트리) + architecture(흐름 레지스트리)
        │
Pipeline ── build: providers → load(stat_skip) → diff → chunk+FTS → embed → graph(rule|llm → degree → doc_refs → communities) → wiki → prune → warm_cache
         ── query: sync → providers → [cache] → router → [expand] → fts | vector | graph → fuse → rerank → context → answer → evolve_capture → log
         ── watch: stat scan → build(incremental)
         ── evolve: capture/feedback/review → proposals → HITL → snapshot → apply → regress → promote|rollback
        │
Store(단일 DB) · Profiler(단계 trace + 카운터) · Providers(역할별 LLM/임베더)
        │
CLI = Web API = Web UI(탭: Architecture, Query, Build, Requests, Tuning, Models, System, Search, Graph, Wiki, Evolve, Eval, Log, Console, Config) · MCP
```

설계 원칙:
1. **단일 정의, 다중 노출** — 토글·튜닝·흐름은 한 곳(레지스트리)에 정의하고 CLI/API/UI/문서가 그것을 읽는다.
2. **모든 단계는 stage** — 단계마다 note(항상)/debug/sample 을 남기고, 끄면 `skipped(사유)` 노드를 남긴다. 숨은 비용(프로바이더 초기화, 캐시 적재)도 stage 로 드러낸다.
3. **증분이 기본** — 빌드의 모든 단계가 "변경된 것만" 처리할 수 있어야 하고, 전체 처리(IDF 재적합, 커뮤니티, FTS optimize)는 전체 빌드 또는 명시적 토글에서만.
4. **안전한 진화** — 제안은 데이터만, 적용 전 스냅샷, 적용 후 평가, 악화 시 롤백. 외부 인터페이스는 읽기 전용.
5. **재현 가능성** — mock LLM 으로 전체 배선을 API 없이 테스트할 수 있어야 한다.

## 5. 품질 기준과 검수

- 평가셋 형식: `[{q, expect_docs[], expect_terms[]}]`. 지표: hit@k, MRR, term recall, answer term recall, avg ms, tokens. 채널 조합(matrix) 비교 기능.
- 검수 시나리오(모두 자동화 권장):
  1. API 키 없는 환경에서 설치 → 전체 빌드 → 질의 → 추출식 답변 + 근거 인용.
  2. 문서 20개 추가 후 증분 빌드: 새 문서만 읽고 임베딩, 기존 문서는 stat 스킵, 위키는 변경 엔티티만.
  3. 사이드바에서 vector 를 끄면 trace 에 `vector_search skipped` 가 나타나고 결과가 바뀐다.
  4. 동일 질의 두 번 → 두 번째는 cache_hit, LLM 호출 0.
  5. 튜닝 파일에서 `fts_mode=or` 로 바꾸면 다음 질의 trace 에 반영되고 캐시가 무효화된다.
  6. 👎 + 정정문 → 제안 생성 → 승인 → 회귀 평가 → applied(또는 rolled_back) 이력.
  7. Requests 화면에서 임의의 과거 요청을 열어 단계별 ms·SQL·토큰·debug 메타·(레벨 2) 프롬프트를 볼 수 있다.
  8. Architecture 화면에서 토글을 바꾸면 해당 단계 카드가 즉시 OFF 표시된다.
  9. MCP 클라이언트에서 `wiki_query` 호출 → 인용 포함 답변.
- 성능 기준(참고): 변경 없는 증분 빌드 < 200 ms(수천 파일), 질의 p95 < 500 ms(LLM 제외), 3,000 문서 벡터 메모리 계획을 System 화면에 표시.

## 9. 흔한 함정 (참고 구현에서 실제로 겪은 것)

- 실행 중인 서버가 옛 코드/옛 설정으로 빌드를 수행해 색인이 뒤집힌 사례 → 코드 변경 시 서버 재시작 필수, 빌드 요청은 `requests` 에 남겨 추적.
- `INSERT OR REPLACE` 가 노드의 비정규화 컬럼(문서 참조)을 지움 → upsert 시 보존.
- 프로바이더 자동 탐지(Ollama ping) 비용이 첫 질의에 숨어 있음 → stage 로 노출하고 결과를 캐시.
- hash 임베딩의 밀집 행렬은 청크수×차원×4B → 대규모에서는 차원 축소 또는 외부 임베더.
- 리랭크 헤딩 보너스처럼 전체 지표는 오르지만 특정 문항이 떨어지는 변경은 반드시 튜닝 가능하게 두고 문서화.
- 소규모 평가셋(12문항)에서는 0.05 차이가 1문항 → 튜닝 전에 평가셋을 늘릴 것.
